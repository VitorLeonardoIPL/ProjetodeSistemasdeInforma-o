Cada requisito do enunciado de AMSI, ligado ao que o Word do FrotaGest já define, com como fazer, onde fica na app e porquê. Os exemplos de código seguem o estilo das aulas (Singleton, listeners, ViewBinding).

Em resumo

O enunciado de AMSI pede uma app Android com webservice REST e fixa requisitos técnicos concretos: 6 a 10 atividades (algumas fragmentos), Volley, CRUD, SharedPreferences, SQLite, master/detail, menu de configuração do servidor. Este manual pega em cada requisito do enunciado, vê no Word do FrotaGest o que já o cobre e explica como fazer, onde e porquê.

Enunciado→Word (RF-AM, US, serviços)→como fazer→onde fica na app→porquê
Duas lacunas no Word: não há menu de configuração do servidor (o enunciado exige) e não há a operação alterar (PUT) numa requisição para o Colaborador (o enunciado exige as 4 operações CRUD). Estão nos passos 4 e 8. A app Android deste manual é a do Colaborador (por agora, só este role usa a app).

5Volley e não bloquear a interfaceapp: pasta de rede/Singleton



O que diz o enunciado


  • "Para o acesso ao webservice é obrigatória a utilização da biblioteca Volley. A utilização de outra biblioteca não será contabilizada para efeitos de avaliação."
  • "O acesso aos recursos do webservice não pode bloquear a interface gráfica."


O que o Word dá


Os 27 serviços REST da secção 9 (JSON, token no cabeçalho Authorization: Bearer, códigos 400/401/403/404/422).


Como fazer


  1. Adiciona a dependência do Volley (com.android.volley:volley) e a permissão INTERNET no Manifest.
  2. Cria uma só fila de pedidos num Singleton, no estilo do SingletonGestorLivros das aulas, e um método por serviço. O resultado chega por um listener:


SingletonFrotaGest.java (exemplo)


LoginListener.java (a interface)


A Activity implementa a interface, regista-se no Singleton (setLoginListener(this)) e chama loginAPI(...) no clique do botão.


Porquê


  • O Volley põe o pedido numa fila e executa-o noutra thread. A resposta só volta quando chega, por isso o ecrã nunca fica parado. Fazer rede na thread principal é proibido pelo Android (NetworkOnMainThreadException).
  • O Singleton garante uma só fila Volley e um só ponto onde estão os pedidos: é o padrão que as aulas usam nos livros.
  • Só Volley para falar com a API. Qualquer outra biblioteca de rede (Retrofit, OkHttp direto) não conta para a nota.


Atenção: para ler o JSON usa as classes do Android (JSONObject, JSONArray) como nas aulas. Evita acrescentar bibliotecas que não são precisas.


Verifica: o login chama a API, o ecrã continua a responder durante o pedido e a resposta chega ao listener.

RequisicoesFragment.java (clique numa linha)


  1. O detail lê o id e pede à API o detalhe (GET /requisicoes/{id}):


RequisicaoDetalheActivity.java

O que diz o enunciado

A lacuna


As 4 operações têm de existir sobre alguns dados. Hoje, para o Colaborador, faltam o alterar das requisições. Propostas (decide com quem faz a API):


  • Requisição: acrescentar PUT /requisicoes/{id} para editar um pedido ainda pendente (datas, motivo, destino). Com isso fica C (POST), R (GET), U (PUT) e D (DELETE) no mesmo recurso, o caso mais limpo.
  • Fatura: acrescentar GET, PUT (corrigir litros/valor, que o RF-AM-13 diz serem editáveis) e DELETE. Seria a 2.ª funcionalidade com CRUD.
  • Notificação: GET + PUT lida (+ DELETE opcional) como 3.ª.
  • Checklist: POST + GET (+ PUT a corrigir o km) como 4.ª.


Como fazer (exemplo de Alterar e Remover com Volley)

Porquê


  • O CRUD é obrigatório e vale muito na avaliação do código. Convém ter um recurso com as 4 operações completas, e demonstrá-las na prova oral.
  • O Word fala em "cancelar" (DELETE), mas não em "alterar" o pedido: é a única operação em falta.


Atenção: alterar uma requisição precisa também de ser feito no website/API (Yii2). Avisa quem faz a API (SIS) cedo.

11SQLite (obrigatório) e modo offlineoffline/FilaOffline.java



O que diz o enunciado


"SQLite para o armazenamento numa base de dados local. Não serão contabilizadas implementações que utilizem alternativas ao SQLite, nomeadamente a biblioteca Room."


O que o Word dá


  • RF-AM-14: guardar localmente fotografias, quilómetros, checklist e pedidos preenchidos sem ligação e sincronizá-los quando houver ligação, indicando os registos por sincronizar.
  • RNF-05 e US6: sem perda de dados. Serviço POST /sincronizacao (envio em lote, cada registo com id_local).


Como fazer


  1. Cria uma classe que estende SQLiteOpenHelper (não uses Room) com uma tabela de registos pendentes:


FilaOffline.java (exemplo)


  1. Quando não há rede (ou o pedido falha por falta de ligação), guarda aqui em vez de falhar.
  2. Quando a rede volta, lê a tabela, envia tudo em POST /sincronizacao e apaga só os registos que a API confirmou.

Perguntas para o estudo


Posso usar outra biblioteca além do Volley?
Para aceder ao webservice não conta para a avaliação. Para ler JSON usa as classes do Android (JSONObject, JSONArray), como nas aulas.


Posso usar Room em vez de SQLite?
Não: "não serão contabilizadas implementações que utilizem alternativas ao SQLite, nomeadamente a biblioteca Room". Usa SQLiteOpenHelper.


O que é uma atividade "construída de forma dinâmica"?
Aquela cujo conteúdo vem do webservice em execução, e não escrito no layout (como o Livro Dinâmico da ficha).


Qual a diferença entre SharedPreferences e SQLite aqui?
SharedPreferences: poucos dados simples (endereço, token). SQLite: registos mais estruturados e em número variável (os pendentes do modo offline).


O que torna uma funcionalidade um CRUD?
Fazer, por serviços da API, as quatro operações: inserir (POST), consultar (GET), alterar (PUT) e remover (DELETE).


Se o código não compilar na entrega?
A classificação é 0 valores no projeto. Compila e testa num emulador limpo antes de entregar.


Preciso mesmo de ter menu de configuração?
Sim, é obrigatório. É por onde se escreve o endereço do servidor, que depois fica nas SharedPreferences.


Erros que podem acontecer


Passa de 10 atividades
O recomendado é 10 no máximo. Junta ecrãs (diálogos em vez de Activities) para ficares dentro.


"NetworkOnMainThreadException"
Foi feito um pedido de rede na thread principal. Usa o Volley (assíncrono), nunca HttpURLConnection direto.


401 em todos os pedidos
Falta o cabeçalho Authorization: Bearer token no getHeaders(), ou o token não foi guardado.


Cleartext HTTP traffic not permitted
Servidor em http: acrescenta android:usesCleartextTraffic="true" no Manifest (só para desenvolvimento; em produção, HTTPS).
